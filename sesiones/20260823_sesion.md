# Sesión — Polla Liga Pro: fixes de deploy, cookies, ranking y scraping de resultados

**Fecha:** 2026-08-23
**Proyecto:** `01_vicente/00_Gestion_procesos_vm/11-polla-ligapro`

---

## Objetivo

Resolver una serie de incidencias en producción (deploy caído, sesión que no persiste, resultados desactualizados) y mejorar la vista de Ranking, todo detectado y solicitado por Vicente durante el uso real de la app con los 10 jugadores.

## Resumen

### 1. ImportError en producción (caché de deploy atascada)
Streamlit Cloud fallaba con `ImportError: cannot import name 'enviar_todos_predijeron'` pese a que el código en GitHub era correcto (verificado con `git show origin/master:email_notif.py`). Se determinó que era un despliegue con caché vieja atascada (coincidió con un salto de imagen Python 3.14.2→3.14.7 entre corridas del historial de logs). Se resolvió con un **Reboot app** manual desde el dashboard de Streamlit Cloud. Como prevención, se agregó `runtime.txt` fijando `python-3.13` para reducir el riesgo de que un cambio de imagen base coincida con un deploy silencioso.

### 2. "Mis predicciones" mostraba la fecha equivocada por defecto
El selector de fecha arrancaba en la ronda con el número más alto cargado en el fixture (ej. Fecha 27, aún sin jugar) en vez de la fecha vigente (26, con partidos en curso). Se corrigió `selector_fecha()` para aceptar un `ronda_defecto`, calculado como la fecha más próxima que todavía tiene partidos sin cerrar.

### 3. GitHub Actions no traía resultados (bloqueo de Cloudflare)
El workflow de sync cada 3h marcaba "success" pero devolvía 0 resultados nuevos, mientras que la misma corrida en la PC de Vicente sí funcionaba al instante. Diagnóstico confirmado: Cloudflare bloquea/limita con más frecuencia las IPs de datacenter de GitHub Actions que una IP residencial. Se deshabilitó el cron automático del workflow (queda solo disponible para disparo manual) y se migró el sync a **tareas programadas de Windows** en la PC de Vicente:
- `PollaLigaPro_SyncResultados` — cada 3h, siempre corre (respaldo general).
- `PollaLigaPro_SyncResultadosVentana` — cada 15 min, pero solo hace scraping real si detecta un partido en ventana activa (`hay_partido_en_ventana()`), para no desperdiciar recursos.
- Posteriormente reemplazado/complementado por **disparos puntuales por partido** (ver punto 6).

### 4. Bug real: marcador parcial guardado como resultado final
Se detectó que Barcelona SC vs Orense quedó guardado como 0-0 cuando el resultado real (confirmado contra SofaScore) era 3-0. Causa raíz: el endpoint `/events/last` de SofaScore trae partidos en cualquier estado (en vivo, entretiempo, finalizado), y el código solo verificaba que `homeScore`/`awayScore` no fueran `None` — esos campos también existen con el marcador **parcial** durante el partido. Un sync que corrió mientras el partido seguía en juego grabó ese parcial como definitivo, y como la query de "pendientes" solo trae partidos con `gl_real IS NULL`, el error nunca se autocorregía. Se corrigió:
- El dato en producción (0-0 → 3-0, con recálculo automático de puntos vía la vista `v_puntos`).
- El código: ahora exige `status.type == "finished"` antes de guardar cualquier resultado como definitivo.

### 5. Búsqueda de alternativas de API en tiempo real (descartadas)
A pedido de Vicente, se investigaron alternativas al scraping para traer resultados en tiempo real:
- **API-FOOTBALL** (free tier): tiene LigaPro Ecuador en su cobertura y 100 requests/día, pero el plan gratuito **no da acceso a la temporada 2026 en curso** (solo históricos 2022-2024) — descartado tras probarlo con una API key real.
- **TheSportsDB** (free tier): sí tiene LigaPro Ecuador 2026, pero cada endpoint devuelve solo 1-5 eventos (no cubre una fecha completa de 8 partidos) — descartado tras pruebas reales.
- Conclusión: ninguna API gratuita da cobertura completa y en vivo de una liga menor como LigaPro; ese nivel de dato está detrás de planes de pago. Se optó por seguir con el scraping local a SofaScore.

### 6. Disparos puntuales por partido (kickoff + 2h15min)
En vez de sondear cada 15 min durante toda la ventana de un partido, se implementó `programar_disparos_puntuales()` en `sync_polla.py`: crea, vía Task Scheduler (PowerShell `Register-ScheduledTask`), un disparo `ONCE` por cada partido pendiente, exactamente a `kickoff + 135 min` (2h de partido + 15 min de margen). Detalles:
- Usa `StartWhenAvailable` para que el disparo corra igual si la PC estaba apagada en ese momento exacto (se ejecuta en cuanto vuelve a encenderse).
- Se encadena automáticamente al final de `sync_polla.py fixture` (programa los disparos de la fecha recién subida).
- `sync_polla.py resultados` ahora limpia (`limpiar_disparos_completados()`) las tareas `ONCE` ya disparadas de partidos que ya tienen resultado, evitando acumulación de tareas muertas.
- Probado en vivo: se programaron y dispararon correctamente los 3 partidos restantes de la Fecha 26.

### 7. Ranking: simplificación y luego ajuste fino de columnas
Primera iteración: se quitaron las tarjetas repetidas + expander "Ver tabla completa", dejando solo una tabla siempre visible con emojis (🥇🥈🥉, 🎯✅⚽).
Segunda iteración (feedback de Vicente: se veía muy cargado en celular): se quitaron los emojis de las columnas numéricas y se marcaron como angostas (`width="small"`) para que quepa completa en pantallas pequeñas.
Tercera iteración (pedido explícito de nuevas columnas, validado con maqueta HTML antes de codificar): se renombró "Pts" → "Puntos Totales", se eliminó la columna "Jugados", y se separó el conteo de aciertos en dos columnas con headers de dos líneas — "Ptos Resultado / Exacto" y "Ptos Resultado / Gana/Empata/Pierde" — sin cambiar el reglamento de puntos (ambos tipos de acierto siguen valiendo 1 punto cada uno; solo se desglosa cómo se llegó al total).

### 8. Sesión persistente por cookie (con una regresión corregida en caliente)
Se implementó sesión de 30 días con `streamlit-cookies-controller`: al iniciar sesión se guarda una cookie con `jugador_id`; si existe al cargar la app, se restaura sin pedir PIN. Cerrar sesión borra la cookie.
Vicente reportó que igual le seguía pidiendo el PIN al volver más tarde. Se intentó reforzar con un `st.rerun()` extra para darle tiempo al componente de cookies a resolver su valor real — pero esto **expuso un `TypeError` en producción** (`if name not in self.__cookies` con `self.__cookies is None`), un bug latente de la librería que el rerun forzado disparaba. Se revirtió el rerun extra (causa raíz del estado intermedio) y se blindó `cookies()` / `restaurar_sesion_desde_cookie()` contra ese `None` con manejo defensivo. Este fix se pusheó de inmediato por ser un crash activo en producción.

### 9. Verificación de salud general
A pedido de Vicente, se hizo un chequeo integral: deploy de Streamlit Cloud (cargando bien, sin errores de import), últimas 5 corridas de GitHub Actions (`success`), datos en Supabase (10 jugadores, 9 con email, Fecha 26 con resultados correctos), tabla `notificaciones_enviadas` sin duplicados, y estado de las tareas programadas de Windows (todas con `LastTaskResult: 0`).
